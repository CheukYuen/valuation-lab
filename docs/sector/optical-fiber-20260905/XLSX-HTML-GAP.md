## 二、发现的三类差异

### A. 结构：完整数据是线性清单，不是表格

`html_audit.py:appendix()` 原先把每张工作表渲染成 3 列清单 `追踪编号 | 原始值 | 公式/来源/格式`，共 2,024 行。读者看不出表格形状，无法横向读一行、纵向比一列；27 个合并区域虽然已存在 `workbook_data.json`，但从未被渲染。

**已修复**：每张表新增按 `max_row × max_col` 渲染的真实二维网格，带列字母表头、行号栏、合并区域、冻结窗格。单元格右上角 ƒ 链到该公式的复算过程并自动展开，带虚线下划线的格子挂着原始来源批注。每张表上方另有一条工具条（排序 / 筛选 / 冻结首列 / 还原顺序），见第三节。原 2,024 行台账保留在网格下方的折叠块里，作为原始精度与来源批注的审计链。

### B. 显示格式已提取但未应用

`format` 字段一直在 JSON 里，渲染时用的却是原始值。1,304 个单元格因此显示成错误形态：

| 出现次数 | number_format | 修复前 | 修复后 |
|---:|---|---|---|
| 918 | `0.00` | `27.527401` | `27.53` |
| 172 | `#,##0.00;[Red](#,##0.00);"—"` | `2310.5978` | `2,310.60`（负数红色括号） |
| 81 | `yyyy-mm-dd` | `2020-01-23T00:00:00` | `2020-01-23` |
| 67 | `0.0%;[Red](0.0%);"—"` | `0.45622879489772616` | `45.6%` |
| 25 | `#,##0` | `288777000` | `288,777,000` |
| 12 | `0.0` | 原始浮点 | 一位小数 |
| 10 | `0.00000` | 原始浮点 | 五位小数 |
| 8 | `0.00%` | 原始浮点 | `6.30%` |
| 7 | `0.0000;[Red](0.0000);"—"` | 原始浮点 | 四位小数，负数红括号 |
| 3 | `0.00"x"` | `1.0976869633639328` | `1.10x` |
| 1 | `0.00%;[Red](0.00%)` | 原始浮点 | `1.23%`，负数红括号 |
| 720 | `General` | 正确 | 不变 |

**已修复**：`html_audit.py` 的 `render()`，只实现上述 12 种格式，不做通用 Excel 格式引擎。格式化在 Python 构建期完成，页面里是真实文本 —— Ctrl+F 能搜、打印正常、零运行时开销。原始值保留在 `data-raw` 属性和审计台账中；公式复算仍走原始精度路径。

三段语义核实结果：

- 负数段 `(#,##0.00)` 是**括号替代负号**并标红，全簿 16 个负值单元格走这条分支。
- 零值段全簿 **0 个单元格命中**，`"—"` 是死分支。空白单元格渲染为空 `<td>`，绝不显示 `—`。

格式引擎的基准是手写断言，不是 openpyxl —— openpyxl 只给原始值和格式码，文件里没有缓存的显示文本，拿它当基准等于自己比自己。24 条断言在 `tests/test_xlsx_format.py`。

### C. 六类属性根本没进 JSON

`migrate_workbook.py` 只提取 ref / value / formula / comment / format / merges，以下全部丢失：

| 属性 | 原工作簿实际值 |
|---|---|
| 冻结窗格 | 六张表均为 `A7`（前 6 行为标题与表头块） |
| 列宽 | 每表不同，6–55 字符（`来源与缺口` E=55、F=53；`投行研报` I=40） |
| 行高 | 24 / 34 / 42 / 45 / 55 / 65 / 66 pt，标记表头行与长文本换行行 |
| 填充色 | 表头带 `#285F8F`；斑马纹 `#F3F6F9`；`行业需求` 高亮块 `#FFF2CC` |
| 字体 | Arial；粗体；18 / 10 / 9 pt；字色 `#172B4D` `#475569` `#FFFFFF` `#0000FF`（行业需求）`#00804A`（估值快照） |
| 对齐 | `vertical=center`、`wrap_text`；`showGridLines=False` |

**已修复**：`migrate_workbook.py` 一并提取，写进 `workbook_data.json` 的顶层 `style` 段（单元格字典结构不变——`verify_artifacts.py` 对它做精确比对）。3,606 个单元格的样式去重成 23 项调色板，映射为 CSS 类 `.xs0`…`.xs22`，避免逐格内联样式。

列宽换算 `px = width × 7 + 5`，其中 7 是 Excel 对 Arial 10 的最大数字宽度；浏览器实测 Arial 10pt 数字步进为 7.41px，与 Excel 同源，因此列内可见字符数一致。行高换算 `px = height × 4 / 3`。

**列宽还原度实测**：66 个数据列中 64 个渲染宽度与工作簿声明值完全一致；`行业需求` 的 F 列（96 → 118.6px）和 K 列（96 → 105.3px）因为 `杰富瑞DC需求占比`、`2026至2028规划` 这类不换行文字超出列宽而被撑宽。表格用自动布局而非 `table-layout:fixed`：Excel 遇到这种情况是把文字溢出到右边的空单元格里显示，本页是把列撑宽，机制不同但**都不隐藏任何字**。没有一列比声明值窄。这两列已写进 `verify_html.mjs` 的断言，多出第三列会直接失败。

打印同理：打印样式把网格压到页宽，因此网格单元格在打印态改为换行而不是裁切（`white-space:normal;overflow:visible`）。已用 Chrome 导出 PDF 并抽取文字层核对，`杰富瑞DC需求占比`、`2026至2028规划` 及全部格式化数值均完整出现在纸面上。

## 三、网格上的交互（原生实现，无第三方库）

曾经做过一版 `index-tabulator.html` 做对照，结论是不用。Tabulator 是数据网格不是电子表格，而这份工作簿的每张表都不是平表——标题块 + 表头 + 数据 + 注释 + 第二张子表堆在同一张 sheet。它会把 18 个标题块合并降级成纯文本、把 9 个数据区的整幅注释压回 A 列截断（`公司财务!A21` 变成 `L1 / L4 公司财…`），还丢掉逐行行高。那个文件和 `vendor/tabulator.*` 已删除。

需要的几项能力改用原生 JS 实现在 `html_audit.js` 末段（约 90 行，页面仍是单文件零依赖，网格仍是真 `<table>`）：

| 能力 | 做法 |
|---|---|
| 表头排序 | 点原表的深蓝表头单元格，升序 → 降序 → 还原三态，带 ▲▼ 指示 |
| 逐表筛选 | 工具条输入框按文本隐藏数据行，标题块、表头和注释块不动 |
| 列宽拖拽 | 拖列字母表头的右边缘，改的是 `<colgroup>` 的宽度 |
| 冻结首列 | 勾选后 A 列 `position:sticky`，与原表按 `A7` 冻结的前 6 行叠加 |
| 区域复制 | 不需要代码。选中真 `<table>` 复制，浏览器把 `text/html` 放进剪贴板，Excel 粘出来就是单元格 |
| 还原顺序 | 一键清掉排序与筛选 |

**排序按「块」进行，不会打乱整张表。** 构建期用原表的深蓝表头带（填充 `#285F8F`）切分区块，整幅合并的注释行和空行是分隔符，只有块内数据行会移动：

| 工作表 | 可排序块 | 各块数据行 |
|---|---:|---|
| 公司财务 | 3 | 7 / 2 / 2 |
| 行业需求 | 2 | 9 / 7 |
| 估值快照 | 2 | 7 / 7 |
| 历史估值 | 2 | 81 / 7 |
| 来源与缺口 | 1 | 18 |
| 投行研报 | 3 | 6 / 6 / 4 |

排序时**行号跟着数据走**（排完 A 列可能显示 13、12、7、10…），所以每个 `data-ref` 始终指向它在原工作簿里的真实坐标，审计链不会因为排序而失真。这与 Excel 的行为相反——Excel 让行号留在原地——但对一份要能逐格追溯的文件，前者才是对的。

Playwright + 本机 Chrome，断网 `file://` 加载，1440×1000：

| 指标 | 值（三次实测） |
|---|---:|
| 文件体积 | 2,611 KB |
| 首次加载 wall | 142 / 147 / 152 ms |

| 展开六张表 | 37–39 ms |

**本页没有 ECharts**，八张图是构建期生成的静态内联 SVG，零运行时依赖，不存在"图表库 + 表格库叠加"的场景。滚动稳定在 60fps，加载期没有 long task。

改动前的旧版本（线性清单、无网格、无交互）加载约 90ms、24,096 节点；补上 3,074 格网格和网格交互后是 142–152ms、28,466 节点。当时的 Tabulator 对照版则要 201ms、32,142 节点、多 135KB 体积——原生实现拿到同样的排序筛选，省下了这笔开销。

## 五、验收

```bash
cd docs/sector/optical-fiber-20260905
npm install --no-save --ignore-scripts playwright   # 只为跑验收脚本；页面本身零依赖
python3 migrate_workbook.py           # 一次性；正常构建不跑

```

验收结果 PASS，覆盖：

- 离线加载、网络请求数 = 1、无 pageerror
- 379 个公式浏览器复算与原缓存一致
- 2,024 行审计台账、8 张 SVG、16 个 section
- 网格单元格数由内嵌数据推导，不写死：3,074 格 / 27 个合并区域
- 格式化文本按单元格地址断言：`公司财务!H7`→`45.6%`、`估值快照!B7`→`2,310.60`、`历史估值!A7`→`2020-01-23`、`行业需求!B7`→`288,777,000`、`估值快照!J25`→`1.10x`、`公司财务!J9`→`(27.7%)` 且带红色类、`公司财务!E19`→`(7.95)`
- 冻结窗格实测生效

- ƒ 标记点击后确实展开对应的复算过程
- 桌面与 390px 均无横向溢出；打印态 8 张图仍在，六张表全部自动展开，网格单元格全部换行不裁切
